# AOSP source patches for xdplus LOS 18.1

Edits to upstream AOSP/LineageOS repos this port needs (can't live in the device tree). Apply from the repo root before `mka bacon`. One patch per subject; a subject that spans two bugs on the same file/subsystem is a single patch.

⚠️ **Numbers are retired, never reused.** `0018`, `0019`, `0028`, `0029`, `0035`, `0039` and `0041` are absent on purpose. `0018` was the SurfaceFlinger hardware-vsync watchdog, cut in the pre-release watchdog audit: it fired several times a minute on a healthy idle device (SF disables hardware vsync when nothing is drawing, the timer expires anyway, and the kick then early-returns), its stage-1 kick was watched failing on the one wedge it existed for, and its stage-2 power bounce was unreachable — the one-shot timer only re-arms on a vsync a real wedge never delivers. `0017`'s hotplug re-arm, which it had refactored, is restored inline and now reverse-checks standalone. `0039` rotated without the screen rotation animation while a second display was attached, to stop the rotation producing transforms no overlay can express. It did exactly that and still did not keep the mirror, because the mirror is lost whenever the primary's visible layer list collapses to one layer, rotating or not; the `xdplus-mirrorpin` service held a layer and covered every case, so the patch was dropped rather than shipped as a disabled option (the service itself was retired later, once the composer stopped needing it). `0035` held the KNOWN-BAD forced-validate experiment for the internal display; it was captured on 2026-08-15 and **deleted the same day** once it was clear that shipping a documented dead end in the series was worse than losing it — the patch body is still recoverable from this repo's history at `3e34b6f`, and the experiment's two negative results are recorded in the working notes, so nothing is lost but the code. `0028` (the microSD setattr EPERM fallback) went when `packages/providers/MediaProvider` was forked and became a manifest project. ⚠️ **`0041` (SAE external auth on MT6630 gen3) went the same way, and it is the case to remember, because the patch outlived the fork by four days and went stale in the gap.** `external/wpa_supplicant_8` became a manifest project pointing at the `Keyaku` fork, which made the patch a duplicate of a change the fork already carried; the fork then gained a second commit (external-auth routing through the driver event handler) that the patch never captured, so it stopped reverse-applying. Nothing was lost — the fork is pushed and the manifest pulls it — but a patch that duplicates a manifest project is a trap: it reads as the record of the change while the real record moves without it. ⚠️ **`0029` (the GPD XD+ Settings menu) went for the opposite reason — `packages/apps/Settings` is NOT forked.** The menu became `parts/` in this device tree, an app Settings discovers as an injected tile, so nothing has to be carried on a Settings branch at all. `0019`: it bound the spare "Gamepad Mapper" button to an HDMI display-freeze recovery, and the button has been unbound for the first release so it can be given its own purpose later. Renumbering the series to close the gap would rewrite every later patch, its README row and its apply line for no gain, so the gap stays.

| 0013 | `frameworks/opt/net/wifi` | `ClientModeImpl`: fix the `WifiInfo` Wi-Fi-standard label on the MT6630. Two parts. **(a) `updateWifiInfoAfterAssociation()` is called at `COMPLETED`, not `ASSOCIATED`.** The supplicant only publishes the negotiated PHY mode once the link is up, so at `ASSOCIATED` `getConnectionCapabilities()` frequently returns `WIFI_STANDARD_UNKNOWN`; the standard is computed exactly once per connection and never revisited, so whatever is read there is latched for the whole connection. ⚠️ **The old note here claimed the HAL "never" reports the PHY mode — that is false and it mattered.** On a connect that goes straight to 5 GHz the HAL reports `11AC` and `Max Supported Tx` reads 433 Mbps; the UNKNOWN case is a timing window, not a permanent property of the chip. **(b) The band fallback no longer trusts a frequency it may not own yet.** When the HAL does report nothing, label by band — the FULLMAC firmware negotiates VHT on 5 GHz (verified 2026-07-17: VHT80 MCS9, 433 Mbit/s @5805 MHz) and HT-only on 2.4 GHz — but `mWifiInfo`'s frequency for *this* connection is written later in `handleSupplicantStateChange()` (from the scan-detail cache) and by the first RSSI poll, so at association time it still holds the **previous** link's value, or `-1` after a `WifiInfo.reset()`. `getCurrentFrequencyMhz()` prefers `mWifiInfo`, falls back to the scan-detail cache for the current BSSID, and returns `-1` when neither knows; on `-1` the standard is left `UNKNOWN` rather than guessed. ⚠️ **Symptom this fixes**: associate to 2.4 GHz first and then move to a 5 GHz SSID and the link reads **Wi-Fi 4 at 5580 MHz** forever, because the fallback evaluated the stale 2437. Reproduced both ways on device 2026-08-25. Cosmetic only — the radio was always VHT. **Unconditional since 2026-08-04** (it was gated on `persist.sys.wifi_standard_11n_fallback` and exposed as a Settings toggle, which only offered a choice between a correct label and a wrong one); the `WIFI_STANDARD_UNKNOWN` guard is what keeps it narrow, so a HAL that does report wins automatically. |
| 0014 | `frameworks/opt/net/wifi` | `SelfRecovery` + `ActiveModeWarden`: make `REASON_STA_IFACE_DOWN` recoverable. | 0031 | `system/vold` | `Exfat::Mount`: drop `MS_DIRSYNC` for exfat public volumes. Deleting a large tree from the microSD through the Files app silently failed — the progress notification ran and the folder was still there. DocumentsUI passes the tree root to `ExternalStorageProvider` as a single `deleteDocument` call and `FileSystemProvider` recurses the whole tree inside that one binder transaction; with `MS_DIRSYNC` every directory entry costs a synchronous card flush (`exfat_sync_inode(dir)` per unlink), so a 24k-entry tree runs for minutes, AMS declares the provider unresponsive (`Reason: ContentProvider not responding`) and kills it mid-walk with nothing propagated back to the caller. Measured on the shipped card, 2000 empty files: unlink 10.54 s → 0.04 s, creation 18.16 s → 1.97 s. **Deliberate divergence** — AOSP master and current LineageOS both set the flag on exfat, vfat and ntfs alike, as the FAT-family substitute for a journal, and a filesystem change does not avoid it (ext4 as a portable volume takes `MS_DIRSYNC` too, and measured no faster under it). It costs less than it appears: the flag covers directory metadata only, file contents are buffered regardless, so a hot eject was never safe and still is not; upstream itself omits the flag for adopted storage on a physically identical ejectable card. The driver's `delayed_meta` batching and `errors=remount-ro` are untouched. `Vfat.cpp` and `Ntfs.cpp` deliberately left on upstream behavior. |
