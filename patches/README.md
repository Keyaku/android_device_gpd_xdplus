# AOSP source patches for xdplus LOS 18.1

Edits to upstream AOSP/LineageOS repos this port needs (can't live in the device tree). Apply from the repo root before `mka bacon`. See `../../../../docs/PORTING_LOG.md` for the why of each. One patch per subject; a subject that spans two bugs on the same file/subsystem is a single patch.

| Patch | Repo | What |
| --- | --- | --- |
| 0001 | `system/core` | init `subcontext` null-guards — pre-P (API-27) vendor leaves `subcontext` null. Guards both `SubcontextChildReap` (init SIGSEGV on boot) and `SubcontextTerminate` (reboot path: without it init SIGSEGVs in the powerctl handler and the fatal-signal handler force-reboots to `bootloader`/fastboot instead of completing — the "reboots drop to fastboot" quirk). |
| 0002 | `system/core` | logd cap_set_proc non-fatal — 3.18 kernel lacks ambient caps; restores logcat. |
| 0003 | `system/security` | keystore: prefer the TEE Keymaster3 as the hardware keymaster — the real HW keymaster is a 3.0 HIDL device backed by the MT8173 trustlet (`keymaster@3.0-service.xdplus`, §30), and our software keymaster@4.1 reports SOFTWARE, so enumerate Keymaster3 and take its `TRUSTED_ENVIRONMENT` device (this is what enables real FBE). Gated behind `tryGetService` first: `enumerateKeymasterDevices` CHECK-aborts if a manifest-listed device fails `getService`, and the stale vendor keymaster@3.0 passthrough decl (unloadable, missing O-era SoftKeymaster symbols) would trigger exactly that. `tryGetService` never aborts — it returns the binderized TEE service once `/vendor/manifest.xml` is patched to hwbinder (`keymaster/tee/install.sh`), and null otherwise, falling back to the software keymaster with no boot loop. |
| 0004 | `frameworks/base` | `KeyStore` null-`mBinder` guard — belt-and-suspenders against system_server NPE when keystore is unavailable. |
| 0005 | `frameworks/base` | hwui `GLUtils::dumpGLErrors` non-fatal — old PowerVR driver leaves benign `GL_INVALID_ENUM` after frames; `GL_CHECKPOINT(LOW)` otherwise aborted every app RenderThread. |
| 0006 | `system/core` | init: ignore `capabilities` rc lines on pre-ambient kernels — parser left an EMPTY capset behind, execing netd/wificond/logd with zero caps (netd socket() EACCES → no wifi/network). |
| 0007 | `frameworks/base` | WindowOrientationListener: propose `persist.sys.flat_rotation` while device rests flat — accel is in the clamshell base, so on-table (normal gaming pose) reads flat and stock keeps last rotation. Prop unset/-1 = stock behavior. |
| 0008 | `system/core` | gatekeeperd: accept the MT8173 TEE trustlet's 61-byte password handle (AOSP's `password_handle_t` is 58) — relaxes three strict `!= sizeof` length checks to `<`. Without it, enroll is rejected ("HAL returned password handle of invalid length 61"), PIN never persists, and HW keymaster auth-bound keys fail `BeginOperation:-26`. Needed by the TEE gatekeeper HAL (§31). |
| 0009 | `frameworks/av` | Mic capture (two layers, §48). (a) `DeviceHalHidl::supportsAudioPatches` → `false`: the frozen-8.1 MT8173 vendor HAL implements `create_audio_patch` for output but returns `-ENOSYS` for the capture (device→mix) patch; AF treats that as fatal on input (`AudioRecord start -38`). Forcing no HAL-patch support makes AF use software patches (`setParameters "routing="` → `audio_route`) everywhere — the mode this legacy HAL natively shipped in. (b) `RecordThread`/`MmapThread::createAudioPatch_l`: that software-routing path then failed with `startInput -22` because it seeded the param string from the source device's address, and AOSP hardcodes the built-in mic address to `"bottom"` (`AudioPolicyManager.cpp:4547`) which `audio_device_address_to_parameter()` returns as a bare token (no `key=`) → valueless `bottom=` the vendor HAL rejects with `-EINVAL`. Fix: seed `AudioParameter` from the address only when it contains `'='`; else start empty → clean `routing=X;input_source=N`. Verified: stock recorder + phiola both record real audio. |
| 0010 | `frameworks/base` | `WiredAccessoryManager` accdet plumbing — MT8173 accdet driver never creates `/sys/class/switch/h2w`, so AOSP's `UEventObserver` jack path is dead (no routing switch, speaker never mutes, headset mic never offered). Adds `AccdetObserver`, a light poll of `/sys/bus/platform/drivers/Accdet_Driver/state` (0=out, 1=headset+mic, 2=headphone) that feeds the h2w headset bits through the normal `updateLocked()` path → audio routing, speaker mute, `IN_WIRED_HEADSET` mic, and the `ACTION_HEADSET_PLUG` status-bar icon (§48). |
| 0011 | `frameworks/opt/net/wifi` | `ClientModeImpl` radio-capability fixes for MT6630. (a) `setPowerSave`: pin power-save off when `persist.sys.wifi_ps_pin_off` is set — the MT6630 (gen3) driver mishandles 802.11 power-save and APs low-ack-kick under sustained load (`DISASSOC_LOW_ACK`, §44/§49); every framework re-enable path funnels through this method so an init-rc `iw` write alone is overridden. **Screen-conditional since §94:** the pin only holds while the screen is on (the kick needs sustained interactive transfer); `handleScreenStateChanged` re-asserts PS-off on screen-on and restores PS on screen-off so the radio dozes in standby — pinning PS off unconditionally was the ~0.7 %/h standby-drain regression. (b) `isWifiBandSupported`: force `false` for `WIFI_BAND_6_GHZ` — chip has no 6E radio but the legacy HAL returns phantom 6 GHz channels and the `config_wifi6ghzSupport` overlay is true-only. 5 GHz left on the normal capability path. Props unset = stock behavior. |
| 0013 | `frameworks/opt/net/wifi` | `ClientModeImpl.updateWifiInfoAfterAssociation`: when the MT6630 legacy HAL returns `WIFI_STANDARD_UNKNOWN` (it never reports the negotiated PHY mode) and `persist.sys.wifi_standard_11n_fallback` is set, label the `WifiInfo` standard by band: `802.11ac` on 5 GHz links, `802.11n` on 2.4 GHz. The FULLMAC firmware negotiates VHT on 5 GHz (verified 2026-07-17: VHT80 MCS9, 433 Mbit/s @5805 MHz — see `docs/WIFI_AC_RESCOPE.md`) while 2.4 GHz is HT-only; without this the UI shows an unknown/blank Wi-Fi standard on every connection. Cosmetic only. Prop unset = stock behavior. |
| 0014 | `frameworks/opt/net/wifi` | `SelfRecovery` + `ActiveModeWarden`: make `REASON_STA_IFACE_DOWN` recoverable. The MT6630 BT firmware asserts intermittently (~1 in 5 boots) in `hcit_mtk_stp.c #2452` (HCI vendor cmd `0xfc1a` = set BD address), crashing the combo chip → WMT whole-chip reset → `unregister_netdev(wlan0)` → framework `STA_IFACE_DOWN`. AOSP's default for `STA_IFACE_DOWN` is `recoveryDisableWifi()` (park forever, no retry) — Wi-Fi stays dead until manual toggle. Patch (v2, 2026-07-18): restart instead (toggle off→on, 30 s delay vs default 2 s), throttled on a dedicated budget (4/hour, separate list — the assert can fire 3+ times per boot, so sharing `config_wifiMaxNativeFailureSelfRecoveryPerHour`'s 2/hour would park Wi-Fi anyway). v2 also adds a start-failure retry loop in `ActiveModeWarden`: v1's single restart at +30 s failed live (2026-07-18 20:51) because the chip was still resetting — the HAL's driver-state write hung 37 s then I/O-errored, `Failed to create ClientInterface. Sit in Idle`, no retry, Wi-Fi stuck off. Now `CMD_STA_START_FAILURE` during a `STA_IFACE_DOWN` recovery re-schedules `CMD_RECOVERY_RESTART_WIFI_CONTINUE` up to 6 times, 30 s apart (~3.5 min total window vs the chip's multi-assert reset cycles). See `experiment_patches/wifi_selfheal_bandaid/README.md` for the captured trigger + the bandaid this replaces. |
| 0015 | `frameworks/base` | `LocalDisplayAdapter`: bounds-guard the external display's active config id (§97). Registering HDMI display 1 makes `SurfaceControl.getActiveConfig()` return **-2** for a beat — the HWC path is torn down by an HPD bounce between `Hotplug external disp(1) connect(1)` and the query — and `findMatchingModeIdLocked()` indexes `mDisplayConfigs[configId]` unguarded. Result: `ArrayIndexOutOfBoundsException: length=1; index=-2` on the `android.display` thread, which kills `system_server` ~0.5 s after every HDMI bring-up, tearing the external path down with it (`ext_disp_deinit`, and every later `ext_disp_resume` then bails with `ERROR:EXTD_DEINIT`). Patch returns `NO_DISPLAY_MODE_ID` for an out-of-range id (the caller already handles that by flagging `mActiveModeInvalid`) and clamps the second landmine in `getDisplayDeviceInfoLocked()`, which would otherwise index `mDisplayConfigs[-2]` on the next info refresh. |
| 0016 | `frameworks/native` | `HWComposer::getDeviceCompositionChanges()`: force the slow validate/present path for external displays (§90, prop `persist.sys.xdplus.hdmi_force_validate`, default 1). The MTK blob answers `presentOrValidate()` on display 1 with "present succeeded" while it has internally marked every layer CLIENT, so SF never validates, never learns of the change, never renders a client target, and HWC bypasses the display forever (`[JOB] (1) SET/bypass/no layers`) — monitor stays dark. **This patch had no file until 2026-07-26**: the fix was committed to the tree (`f0015a505e`) but never captured here, so a fresh checkout applying the series would silently lose it and mini-HDMI would regress to the §90 wedge. |
| 0012 | `frameworks/native` | `InputDispatcher`: input lag + its screen-timeout side-effect. Root cause of the ~1 s lag on the 3.18.79+ kernel: `pokeUserActivity()` bottoms out in a synchronous power-HAL `sendPowerHint(INTERACTION)` binder call that stalls the RT dispatcher thread; plus `epoll_wait` with any non-zero timeout intermittently drops the eventfd wake. Fixes: `dispatchOnce` uses `pollOnce(0)+usleep(1000)` (non-blocking, ~1 kHz, 2.5 % CPU); and the user-activity poke is offloaded to a dedicated `InputUserActivity` thread (coalesced, condvar-driven) so the dispatcher never blocks AND user activity still resets the screen timeout (an earlier full stub of `pokeUserActivityLocked` fixed the lag but dimmed/slept the screen mid-gamepad-play). NOT cpuidle/cpusets/schedtune (disproved live). Verified: `mLastUserActivityTime` advances on input, screen stays awake, no dispatcher stalls under burst input. |
